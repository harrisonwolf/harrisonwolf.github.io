Why it exists

Every AI lives in its maker’s app.

Want Claude? Open Claude Code. Want GPT? Open Codex. Want both on the same problem? Now you’re the glue, copying prompts between sessions and carrying context by hand. Orc takes the models out of their walled gardens: any model you can reach plugs in the same way, and a coordinating agent splits the task among Workers, each on whichever model you assign, all at once.

How a run works

A prompt with a spine.

Ask an ordinary AI something and it thinks, calls tools and answers. A run in Orc does the same work as a strict phase machine with explicit gates, several models and a full record: a super-prompt you can inspect before it starts, steer while it runs, and pick up again after it ends. One run, in order:

01 · Conversation

Start by talking it through.

Every project has a conversation model that sits apart from the runs. It sees the project, its runs and its files, you can talk to the watchdogs through it, and when you’re ready it drafts the whole run for you: objective, constraints, models, limits.

Nothing starts until you confirm.

02 · First look

Catch a bad plan before it costs anything.

The coordinator’s first move is a plan, not code: a tool-free first look you proceed, correct or cancel. In one recorded run the coordinator caught an unsafe lookup in Claude’s first proposal and sent it back for hardening; the unsafe version never landed.

Every version of the plan and every correction is kept.

03 · Workers

Any model, any role, any settings.

Pick each Worker’s model from one menu: family, model, reasoning effort. A frontier model on the hard part, a cheap one on the chores, paid by API key or the subscription you already have. Workers run at the same time, each in its own private copy of the project.

Mix providers inside one run.

04 · Steer

Change course mid-run.

Message the run, interrupt the coordinator, or have it dispatch another Worker on a different model partway through. A run-control policy says which of those an agent may do alone, which need your confirmation and which are off-limits; proceeding, correcting and abandoning are always yours.

05 · Watchdog

Something is always watching.

A watchdog is a separate agent that observes the Workers and keeps a running report: it updates as the run unfolds, flags what goes wrong, and answers your questions during the run or after it closes. Every version of its notes is kept.

06 · Review

Nothing lands unchecked.

Workers propose; they never write to the shared project. Orc checks each proposal against the exact files the Worker started from, runs builds and tests inside the sandbox, and you accept or reject each one. Imported repositories are never mounted for agents: your original stays untouched until you apply reviewed changes back yourself.

07 · Continue

Pick up where you left off.

A closed run isn’t a dead end. Continue it as a new run seeded from the exact files it retained, and every file stays traceable to the Worker, model, settings and invocation that produced it, down to the content fingerprint of the bytes.

Containment

No agent can go rogue on your machine.

Every model runs sealed inside a container with no off switch. An agent sees only what you’ve explicitly handed it, never your home folder or the rest of your system. Builds, tests and browsers run in their own containers with networking disabled. Your API keys live in an encrypted vault and reach providers only through a local proxy; no model process ever holds one. Until you set a control policy, every agent action is prohibited by default. Loosen it for trusted work, tighten it for risky work: the rules are yours.

For technical readers

Provider-neutral by construction.

No model is built into Orc’s core. A model is an endpoint, a versioned connection behind a common adapter boundary; native provider CLIs, direct API keys and hosted routers all meet the same Workbench boundary, and the coordinator, the conversation model and each Worker can bind to a different one. Everything else belongs to Orc and to the operator, not to any vendor.

Coordinator, client and history

The cockpit is a client of a per-user background daemon, the only supervisor of work. Closing a client never stops a run; restarting the daemon takes over running work within a stated envelope; and code updates are detected and never mixed into work already running. Every control is validated against the task’s current state, so a stale screen can’t trigger a wrong action.

Task state is rebuilt from a validated event journal rather than trusted from a cache, and outputs are stored by content hash. Worker output is captured separately from its working folder, preserving the exact bytes that were reviewed. Cancel, stop, retry and replace each leave a different trace, and a missing result stays visibly missing instead of being read as success.

Workspaces, containment, keys and watchdogs

Containment is deny-by-default. Inside the bubblewrap sandbox nothing from the host is visible unless it is explicitly bound: system libraries read-only, the invocation’s own model area read-write, and any paths the operator declares for that endpoint. Registration refuses /, the home directory itself and protected locations; a program the sandbox can’t see is refused rather than run unconfined. The environment is cleared down to an allowlist, and each run follows an operator-set control policy that prohibits every agent action until one is set.

Workers edit private copies of a managed project folder and propose changes. Integration checks each affected file’s baseline: unrelated changes don’t invalidate a proposal, and stale same-file work is not auto-merged. Imported repositories are never mounted for agents; the operator reviews and applies exact retained changes back with conflict checks.

Build, test and browser tools run in Docker containers. Hosted API keys live in a passphrase-encrypted vault and reach providers only through a local auth proxy; no model process receives a key. Each launched run can carry a watchdog, a constrained agent limited to observing its Workers and writing versioned advisory notes. These are real boundaries, not a VM: containers share the host kernel, and model processes keep network access to reach their providers, while tool containers run with networking disabled.

Live trial and verification

In Orc’s first live trial, five tasks ran against real models, with providers mixed within the same task. One ran six Workers concurrently in a single wave. In another, the implementation Worker timed out and the coordinator still produced a complete 37 KB interactive HTML page from the surviving specialists’ work. A third failed outright when every Worker hit its deadline, and Orc closed it as failed rather than inventing a result.

Separately, a fresh targeted run passed 19 of 19 selected tests covering Worker output retention, follow-up behavior, review binding and history checks. That is a focused check, not a full-suite qualification. A later coding trial completed a small real repository repair, kept the original untouched until a separate reviewed apply, and passed the project’s unchanged tests. Orc is a working prototype, not production software, and the repository is private.

About the interactive recording

The 83-second interactive tour comes from a separate real project on a small public repository (schedule), using GPT-6 Astra as coordinator, Claude Sonnet 5.5 for implementation and GPT-6.1 Sol for the conversation, the watchdog and a steered documentation Worker. Three runs ran in about twelve minutes, including review pauses; the final check passed 52 tests (41 optional timezone tests were skipped because that dependency wasn’t installed). The first run closed as partial because integration was deliberately left to the operator; the continuation runs closed successfully. Steering used a queued message rather than an interrupt. Each run had one watchdog. Two watchdog answers were retained and attributed, but the step that closed each of those invocations failed with an error, which is kept on record. Some retained views (reports, policy, file attribution) were opened through Orc’s own renderers in a read-only viewer. Cuts fall only between screens.

About the tour recording

The 62-second tour is the real terminal application (1920 × 1080, 30 frames per second, no audio), captured from the live session with asciinema, at normal speed. It has one cut, between screens: the first part follows the live run, the second reviews the Workbench afterwards. The Workers finished fast (about 40 and 60 seconds), so the tour starts after the Claude Worker had completed, while the GPT Worker and the coordinator were still running. A few transient terminal redraws are visible; nothing was retouched. An earlier attempt failed before dispatch when Docker could not see its working folder; it is kept on record, and the successful run used the documented location.
