Any AI. One cockpit.
Your rules.

Orc runs any AI model, from any provider, side by side on the same task, from one terminal you control. GPT, Claude, Gemini, Grok, Meta’s Muse, DeepSeek, Kimi, Qwen, open-weight models, even fast decision models like Jev and Clef: mix as many as you like in a single run, each on the part it does best. Every one of them works inside a sealed container, under permissions you set, in a workspace you own.

Why it exists

Every AI lives in
its maker’s app.

Want Claude? Open Claude Code. Want GPT? Open Codex. Want both on the same problem? Now you’re the glue: copying prompts from one session into another, deciding which files each one can see, figuring out where the work lives and carrying context across by hand. Each vendor’s tool decides how its model is allowed to work, and none of them talk to each other.

Orc takes the models out of their walled gardens. Claude and GPT are just the familiar examples: any model you can reach, frontier or open-weight, through an API key or your existing subscription, connects through the same boundary and is picked from one menu: family, model, settings. Any of them can be the coordinator, the one you chat with, or a Worker. A coordinating agent splits the task among Workers, each running whichever model you assign, with its own reasoning settings, all at once. They work on one shared project folder, your API keys stay in an encrypted vault that no model ever sees, and a watchdog agent keeps an eye on each run. Nothing is proprietary, and every rule is yours: which models, how many, what they may touch, and what counts as done.

It works with real models. In its first live trial, Orc mixed providers inside a single task, ran six Workers in one wave, and when one Worker timed out, the coordinator still built a complete interactive web page from the others’ work. Later, it repaired a real code repository end to end, passing the project’s own unchanged tests.

What you can do from the cockpit

You set the rules. The models do the work.

Each step is a point where the operator, not a vendor’s app, decides what happens. Select any screenshot to see it full size.

01 / Brief & plan

Brief once. Approve the plan before anything runs.

Write the task one time, in one place: what to do, what done looks like, what not to touch. No re-pasting it into a second app for a second model. The coordinator, on whatever model you choose, answers with a plan first. Proceed, correct it, or cancel, before a single token is spent on the real work.

Every version of the plan and every correction is kept.

02 / Workers

Any model, any role, any settings.

Let one model write the backend while another builds the UI and a third reviews both. Put a frontier model on the hard part and a cheap open-weight one on the chores, each with its own reasoning effort. Pay through an API key or the subscription you already have. Workers run at the same time and finish independently. If one goes sideways, redirect it, retry it, or swap in a different model, without stopping the rest.

Each Worker’s model, assignment and status are one keystroke away.

03 / Shared workspace

One workspace. Nothing lands unchecked.

All the models work on the same project, not in separate vendor silos. Each Worker edits a private copy and proposes its changes; Orc checks every affected file against the version the Worker started from, so stale work is never silently merged over someone else’s. Bring an existing repository and agents only ever touch an isolated copy: your original stays untouched until you review the exact changes and apply them back yourself.

Every contribution stays tied to the Worker and model that produced it, so you always know who changed what.

04 / Containment

No agent can go rogue on your machine.

Every model runs sealed inside a container, with no way to switch it off. An agent sees only what you’ve explicitly handed it, never your home folder or the rest of your system, so it can’t wander off and delete your files. Each agent may do only what its permissions allow, and even then, its changes are proposals: nothing touches your real work until you review and accept it. Loosen the permissions for trusted work or tighten them for risky work. The rules are yours.

The work runs in a background service, watched by a watchdog agent, so you can close the cockpit mid-task, run several tasks at once and come back to exactly where things stand. Press g for history.

Until you set a control policy, every agent action is prohibited by default.

For technical readers

Provider-neutral by construction.

No model is built into Orc’s core. A model is an endpoint: a versioned connection behind a common adapter boundary, chosen by family, model and settings, with reasoning effort and tool mode as settings rather than separate models. Native provider CLIs (signed in with your own subscription), direct API keys, and hosted routers such as OpenRouter that reach the wider ecosystem all meet the same Orc Workbench boundary. The coordinator, the conversation model and each Worker can bind to a different endpoint. Swapping a provider, or mixing several, is a configuration change rather than a different tool. Everything else (the plan, the Workers, the workspace, the tools, the record, the controls) belongs to Orc and to the operator, not to any vendor.

Coordinator, client and history

The cockpit is a client of a per-user background daemon, the only supervisor of work. Closing a client never stops a run; restarting the daemon takes over running work within a stated envelope; and code updates are detected and never mixed into work already running. Every control is validated against the task’s current state, so a stale screen can’t trigger a wrong action.

Task state is rebuilt from a validated event journal rather than trusted from a cache, and outputs are stored by content hash. Worker output is captured separately from its working folder, preserving the exact bytes that were reviewed. Cancel, stop, retry and replace each leave a different trace, and a missing result stays visibly missing instead of being read as success.

Workspaces, containment, keys and watchdogs

Containment is deny-by-default. Inside the bubblewrap sandbox nothing from the host is visible unless it is explicitly bound: system libraries read-only, the invocation’s own model area read-write, and any paths the operator declares for that endpoint. Registration refuses /, the home directory itself and protected locations; a program the sandbox can’t see is refused rather than run unconfined. The environment is cleared down to an allowlist, and each run follows an operator-set control policy that prohibits every agent action until one is set.

Workers edit private copies of a managed project folder and propose changes. Integration checks each affected file’s baseline: unrelated changes don’t invalidate a proposal, and stale same-file work is not auto-merged. Imported repositories are never mounted for agents; the operator reviews and applies exact retained changes back with conflict checks.

Build, test and browser tools run in Docker containers. Hosted API keys live in a passphrase-encrypted vault and reach providers only through a local auth proxy; no model process receives a key. Each launched run can carry a watchdog, a constrained agent limited to observing its Workers and writing versioned advisory notes. These are real boundaries, not a VM: containers share the host kernel, and model processes keep network access to reach their providers, while tool containers run with networking disabled.

Live trial and verification

In Orc’s first live trial, five tasks ran against real models, with providers mixed within the same task. One ran six Workers concurrently in a single wave. In another, the implementation Worker timed out and the coordinator still produced a complete 37 KB interactive HTML page from the surviving specialists’ work. A third failed outright when every Worker hit its deadline, and Orc closed it as failed rather than inventing a result.

Separately, a fresh targeted run passed 19 of 19 selected tests covering Worker output retention, follow-up behavior, review binding and history checks. That is a focused check, not a full-suite qualification. A later coding trial completed a small real repository repair, kept the original untouched until a separate reviewed apply, and passed the project’s unchanged tests. Orc is a working prototype, not production software, and the repository is private.
